# ADR-003: Cloudflare D1 default; Neon Postgres via recipe

![Status](https://img.shields.io/badge/status-Accepted-brightgreen) ![Date](https://img.shields.io/badge/date-2026--05--09-blue)

## Context

Picking the relational store at the edge has two camps: SQLite-at-edge (D1) gives zero-ops millisecond reads everywhere but caps write concurrency per database; Postgres-via-network (Neon + Hyperdrive) gives full Postgres power but adds another vendor and a TCP-from-Workers dependency. Most internal apps fit the D1 envelope; the few that don't need a clear escape hatch.

## Decision

[Cloudflare D1](https://developers.cloudflare.com/d1/) is the default relational data layer; [Drizzle](https://orm.drizzle.team/docs/get-started-sqlite#cloudflare-d1) is the ORM ([ADR-004](004-drizzle-orm.md)). Migrations live in `drizzle/` as SQL files generated by `drizzle-kit generate`, applied via `wrangler d1 migrations apply`. For apps that outgrow D1 (JSONB, advisory locks, `LISTEN`/`NOTIFY`, write-throughput beyond per-database limits, multi-region multi-master), the planned [`data-layer/switch-to-neon-postgres`](https://github.com/mwheatfill/app-platform-recipes#planned-recipes) recipe swaps to Neon + [Cloudflare Hyperdrive](https://developers.cloudflare.com/hyperdrive/) without changing the ORM API.

## Consequences

**Positive:**

- Zero ops on the data layer; D1 replicates to all Cloudflare locations and reads are millisecond-latency from anywhere.
- Same Drizzle API across SQLite (D1) and Postgres (Neon), so the swap is mechanical.

**Negative:**

- SQLite write concurrency is per-database; high-write workloads need Postgres.
- No JSONB or other Postgres-only features beyond what SQLite + FTS5 cover.
- No cross-region multi-master replication.
