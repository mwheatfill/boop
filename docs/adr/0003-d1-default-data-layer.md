# ADR-0003: Cloudflare D1 default; Neon Postgres via recipe

## Status

Accepted (2026-05-09)

## Context

Apps cloned from this template span a range of data needs:

- Most internal apps: small data (less than 100 GB), modest write volume, simple relational queries.
- Some apps (the web scheduler is one) eventually grow into needing JSONB, complex queries, or run-history at scale.
- Almost no internal apps need cross-region multi-master or document storage.

The default needs to fit the common case. Apps that outgrow it should have a clear, mechanical upgrade path.

## Decision

**Cloudflare D1** (SQLite at edge) is the default relational data layer for apps cloned from this template. **Drizzle** is the ORM ([ADR-0004](0004-drizzle-orm.md)). Migrations live in `drizzle/` as SQL files generated by `drizzle-kit generate`.

**Neon Postgres + Cloudflare Hyperdrive** is documented as a swap recipe (`data-layer/switch-to-neon-postgres`). Apps that need JSONB, Postgres-only features, or scale beyond D1's limits use the recipe.

## Consequences

**Positive:**

- Zero ops: D1 ships with the Cloudflare account; no separate database service to provision, monitor, or pay for at low volume.
- Edge-fast reads: D1 replicates to all Cloudflare locations; reads from anywhere are millisecond-latency.
- Drizzle dialect support means the ORM API is identical between D1 and Postgres; the swap is mechanical.
- Pricing aligns with the rest of the Cloudflare bill.

**Negative:**

- SQLite limits: write concurrency, no JSONB, no `LISTEN`/`NOTIFY`, no advisory locks, no full-text-search beyond FTS5.
- D1 has per-database size and request-per-second limits that production apps may grow into.
- Some Postgres features common in mature apps (window functions are present, but stored procedures are not) require workarounds.

**Neutral / trade-off:**

- Apps that start on D1 and migrate to Postgres later pay a one-time recipe-application cost (estimated 10-30 minutes of mechanical work). The trade is "fast bootstrap, occasional swap" vs. "Postgres-from-day-one for every app."

## Alternatives considered

- **Postgres-first (Neon + Hyperdrive default)** — more capable, but adds setup cost for every app even when the app doesn't need it. Loses the "zero ops" property for the common case. The reference app (HoopsLoop) uses this pattern, but HoopsLoop is consumer SaaS with run-history scale; most internal apps don't have those drivers.
- **Traditional managed Postgres (Azure SQL, RDS, Cloud SQL)** — more ops, no edge story, doesn't compose with Cloudflare Workers as cleanly. Lost on ops cost and integration.
- **MySQL via PlanetScale** — capable, but vendor-distance from the rest of the Cloudflare stack. Lost on integration.
- **MongoDB / DynamoDB / document stores** — most internal apps are relational. Lost on fit for the common case.
