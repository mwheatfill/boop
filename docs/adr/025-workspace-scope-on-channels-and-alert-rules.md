# ADR-025: Workspace scope on Channels and AlertRules, additive override hierarchy

![Status](https://img.shields.io/badge/status-Proposed-yellow) ![Date](https://img.shields.io/badge/date-2026--05--12-blue)

## Context

Alerting v1 ([PR #55](https://github.com/mwheatfill/boop/pull/55), [PRD #25](https://github.com/mwheatfill/boop/issues/25)) shipped `channels.customer_id NOT NULL` and `alert_rules.customer_id NOT NULL` with unique indexes on `(customer_id, slug)`. Every Channel is owned by exactly one Customer; every AlertRule attaches at the Customer level (defaults inherited by all Jobs in that Customer). CONTEXT.md's pre-existing entry called Channel "a reusable outbound destination for alerts, owned by a Customer," and the Operator-level description fixed the workspace as "one (SwitchThink), not per-Customer."

SwitchThink itself is an MSP managing ~270 Customer organizations. The obvious workflow — one SwitchThink-ops Teams channel that all Customer failures route to, plus per-Customer overrides where Acme also wants their PagerDuty pinged — requires 270 duplicate Channel rows and 270 duplicate AlertRule rows under the v1 schema. That duplication is brittle (a webhook URL change ripples to 270 places), discoverable only by reading per-Customer hubs, and out of step with the canonical MSP-monitoring pattern.

The canonical pattern is firmly established by adjacent vendors. **Grafana** contact points are workspace-scoped and referenced by many notification policies. **PagerDuty** integration credentials live at the account level even though escalation policies attach to one Team. **Datadog** and the MSP-tools class (Datto, Halo, ConnectWise) all expose a workspace tier for shared destinations.

Picking poorly here either (a) leaves the MSP ergonomics broken and pushes operators toward seeding workarounds (one AlertRule per Customer that happens to reference the same Teams webhook URL — drift inevitable), or (b) overshoots with a Team / tag-based / multi-tier model that introduces vocabulary boop's domain doesn't yet need.

## Decision

`Channel` and `AlertRule` both gain a `scope` discriminator with values `workspace` and `customer`. The two scopes coexist in the same physical tables. A new top-level UI surface owns the workspace rows; per-Customer hubs continue to own Customer-scoped rows. Override semantics across the resulting three-layer AlertRule hierarchy (workspace → customer → job) are **additive**, not shadowing.

| Concern | Choice | Over |
|---|---|---|
| Naming | **Keep `Channel` and `AlertRule` as umbrella terms with a `scope` discriminator.** CONTEXT.md redefines both to admit workspace + customer scope. One vocabulary, two flavors. | Splitting into `WorkspaceChannel` / `CustomerChannel` (doubles domain terms, forces two UIs); introducing `Subscription` for the per-Customer opt-in (new noun, reshapes AlertRule). |
| Number of scope axes | **Binary: `workspace` or `customer`.** No `Team` axis. | A third `Team` scope (would conflate three possible meanings: Operator sub-group, Customer cluster, the Customer's internal team — none of which exist in CONTEXT.md today); abandoning scope entirely for a tag-based matcher model (Grafana-like; more flexible but indirect for the simple MSP case). |
| Schema discriminator | **`scope TEXT CHECK IN ('workspace', 'customer')` column + nullable `customer_id` + CHECK constraint that customer_id is non-null iff scope='customer'.** Same physical table; the implied state machine is enforced in SQL. | Implicit `customer_id IS NULL` as the workspace signal (sneaky); separate `workspace_channels` table (doubles the alerting consumer's resolution path on the hot lane). |
| Slug collisions | **Allowed across scopes.** Partial unique indexes: `(slug) WHERE scope='workspace'` and `(customer_id, slug) WHERE scope='customer'`. Customer Channel `ops-triage` and workspace Channel `ops-triage` can coexist. The Channel picker disambiguates with a scope pill (`[workspace]` / `[Acme]`). | Reserving workspace slugs across all Customers (defining a new workspace Channel retroactively forbids every Customer's existing slug); `ws/`-prefix namespacing (visual noise on every workspace reference). |
| AlertRule symmetry | **AlertRule gains `scope` parallel to Channel** — `workspace`, `customer`, or `job`. Without this, workspace Channels are a half-measure: the MSP still authors `first_failure → ops-triage` in every Customer. | Channel-only workspace scope (loses the ergonomic win the original problem asks for); deferring AlertRule symmetry to a phase 2 (premature split — the override semantics for workspace are easier to settle alongside Customer/Job than retrofit). |
| Cross-scope channel references | **A workspace AlertRule's `channel_ids` may reference workspace Channels only.** Enforced at write time. A Customer AlertRule's `channel_ids` may reference workspace Channels and Channels of its own Customer (NOT other Customers' Channels). Job AlertRules inherit their parent Job's Customer scope. | Allowing workspace AlertRule → Customer Channel (would silently fan Customer B's failures into Customer A's private SOC channel — cross-Customer leak); allowing Customer AlertRule → other-Customer Channel (same leak class). |
| Override semantics (the verb) | **Additive.** When a Run goes terminal, every matching workspace rule, every matching Customer rule for that Run's Customer, and every matching Job rule for that Run's Job evaluates independently. The union of all matching rules' Channels is the fan-out set (deduped by `channel_id`). No suppression / muting in v1. | Shadow-by-kind (a Customer's `first_failure` hides workspace's `first_failure`; other kinds inherit — requires per-kind precedence logic); shadow-all (any Customer rule suppresses all workspace rules — PagerDuty Team-shaped, but punishes Customers for adopting one custom rule by losing every workspace default). |
| Muting workspace rules per-Customer | **Out of v1.** Opting a Customer out of a workspace rule means an Admin deletes the workspace rule (heavy hammer) or the Customer's set diverges further (still gets fired, plus their own). | Adding a `muted_workspace_rule_ids` array on Customer (new column; new authoring surface; punts decision about what "muting a fired alert" means at the Channel level vs the Rule level). |
| Authorship permission | **Admin only** for CRUD on workspace-scoped rows. All Operators read (so workspace rows show up in Customer-hub pickers). Mirrors the existing Admin gate on per-Customer Channel CRUD ([slice 1 + PR #55](https://github.com/mwheatfill/boop/pulls?q=is%3Apr+channel+author%3Aapp%2Fclaude)). | Operator-write on workspace rows (blast radius — one edit affects every Customer; not consistent with the existing Channel CRUD gate). |
| Lifecycle (archive) | **Per [ADR-019](019-soft-delete-policy.md): archive blocks on active dependents.** Archiving a workspace Channel surfaces the count of active AlertRules referencing it (across all Customers) and refuses until they detach. Workspace AlertRules archive freely (the additive model has no FK dependents). | Cascade-detach (silently rewires alerting); force-archive button (footgun even behind typed confirmation when 270 Customers are involved). |
| UI placement | **Top-level `/channels` and `/alert-rules` in the main sidebar**, Admin-gated. Per-Customer Channels and AlertRules stay in the Customer hub. Each top-level page shows only workspace-scoped rows with a hint linking to per-Customer hubs. | Burying under `/admin/channels` (less discoverable; misaligned with how cross-Customer surfaces like `/jobs` and `/runs` are surfaced); single mixed cross-scope list (mixes scope in the create flow — "new channel from here means what scope?"). |

The alerting consumer's hot path (`src/lib/alert-rules/evaluator.ts`) gets a single additional `WHERE` clause: load rules where `(scope='workspace') OR (scope='customer' AND customer_id=?) OR (scope='job' AND job_id=?)`. The shape of `channel_ids` on the AlertRule row does not change — it stays the JSON-array-of-IDs that PR #55 shipped; the alerting fan-out resolver looks up each channel by ID and the channel row's own scope is incidental at fan-out time.

## Consequences

**Positive:**

- The canonical MSP triage workflow becomes one workspace Channel + one workspace AlertRule, not 270 duplicates. The PRD that lands this ADR delivers an immediate, visible ergonomics win for SwitchThink's primary use case.
- The schema delta is minimal: one column (`scope`), one CHECK constraint, two partial unique indexes per table, `customer_id` becomes nullable. Existing rows backfill to `scope='customer'` in the same migration. No `channel_ids` reshape; no AlertRule→Channel join-table introduction.
- The additive override math is the simplest possible mental model for operators: "every matching rule fires." Three layers can be reasoned about without a precedence chart. Job-level AlertRule overrides (still unimplemented per PR #25's deferred follow-up) land cleanly into the same union-of-matches loop.
- Scope is enforced once at the boundary (the write-time validator on AlertRule `channel_ids` rejects cross-scope leaks), not on the alerting hot path. The fan-out consumer doesn't pay for the scope discipline.
- Symmetric scope on Channel and AlertRule reads consistently in code, UI, and CONTEXT.md. A future reader sees one pattern, not two adjacent ones.
- The Admin permission boundary is unchanged: workspace rows fall under the existing "Admin manages Channels" definition without inventing a new role.

**Negative:**

- One more concept for operators to internalize. The scope pill in the picker is a small but real UI affordance; documentation and DESIGN.md § 5 (filter chips) will need to mention it explicitly. Mitigated by making the pill visually quiet (subtle accent tint, not a bright badge).
- No mute mechanism in v1. A Customer that doesn't want a workspace rule's fan-out has only the heavy option (Admin deletes the workspace rule, breaking every other Customer that depended on it) or accumulates duplicate fan-outs (workspace + their own). A follow-up `muted_workspace_rule_ids` column on Customer is the path forward when a real user story emerges; deferring keeps v1 unambiguous.
- The CHECK constraint on `channels` (and on `alert_rules`) tightens the schema vs. the v1 shape. Existing tooling that writes Channel rows must produce `scope='customer'` and a non-null `customer_id`. The Drizzle layer handles this via the schema; ad-hoc SQL inserts in tests need updating. Single-PR migration handles this in one sweep.
- Slug collisions across scopes mean the AlertRule picker has to render the scope pill consistently — a regression in UI implementation would surface as an apparent "two channels named the same thing" bug. Tests assert the pill renders on every picker entry.

**Neutral / trade-off:**

- Picking `scope` as an enum rather than a boolean flag (`is_workspace`) costs one byte and gains room to add a third value (`Team`-scoped or otherwise) without a column rename. The decision to defer `Team` is recorded explicitly; if a future ADR adds it, the migration is one row in the enum, not a schema reshape.
- The constraint "a workspace AlertRule references workspace Channels only" is enforced at write time, not via a foreign-key relationship (because `channel_ids` is a JSON array). A future "join table" refactor of AlertRule→Channel would convert the runtime check into a DB-level FK predicate; deferred per the PRD #25 design.
- The choice not to add a `primary_customer_channel` indirection means workspace AlertRules cannot include "fan out to each Customer's primary channel" semantics in v1. That feature is the natural follow-up when a real story demands it; recording the rejection here so the next contemplator finds the trail.
- This ADR composes with [ADR-019](019-soft-delete-policy.md) (archive blocks on active dependents — extends to Channels), [ADR-018](018-navigation-ia.md) (top-level cross-Customer surfaces — `/channels` and `/alert-rules` join `/jobs` and `/runs`), and [ADR-016](016-operator-authz.md) (Admin role for workspace authorship; double-bound AI authz applies uniformly when AI surfaces eventually propose Channels). No ADR is superseded.
